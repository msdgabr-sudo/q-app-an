## 1. Purpose of the work

The localization work was not limited to adding translations. The primary goal was to provide Arabic, English, French, Indonesian, and Urdu without allowing language changes to interfere with live compass behavior, camera opening, astronomical verification, GNSS/calculation state, navigation, or protected scientific engines.

Problems encountered and addressed during the rollout included:

- Language switching affecting the live compass.
- Camera/astronomical-verification entry failing after language changes.
- DOM translation touching operational UI.
- A translated language becoming the apparent source text for a later language.
- French text leaking into Indonesian/Urdu after FR -> ID -> UR switching.
- Failure to restore the original Arabic text after a full language round-trip.
- Internal presentation pages being mounted after the language runtime and therefore remaining Arabic.
- PWA/Service Worker cache serving mixed generations of i18n files.

## 2. Supported web languages

The stabilized web/PWA language set is:

- `ar` — Arabic — RTL — source language.
- `en` — English — LTR.
- `fr` — French — LTR.
- `id` — Indonesian — LTR.
- `ur` — Urdu — RTL.

The Arabic UI is treated as the source-of-truth for DOM restoration unless an element carries an explicit source marker.

## 3. Important i18n files

The active/important localization area is `js/i18n/`.

Important files include:

- `english-rollout.js` — historical name, but this is the principal multilingual runtime.
- `home-language-picker.js` — language selection UI/integration.
- `home-phrases.js` — Home presentation translations.
- `general-phrases.js` — general UI phrases.
- `extra-phrases.js` — additional translation coverage.
- `fr-phrases.js` — French additions/overrides.
- `dynamic-patterns.js` — translations for dynamic text patterns.
- `internal-screen-phrases.js` — translations for internal presentation screens.
- `internal-screen-final-phrases.js` — final gap-fill pack discovered during phone testing.
- `internal-screen-language-bridge.js` — applies the selected language to mounted internal screens and supported iframe documents.
- `unified-phrases.js` — transitional consolidation layer. Do not make it the sole production source or remove legacy packs without a new equivalence/phone test cycle.

Some legacy files may still exist but are not necessarily loaded by Production. Never delete a localization file merely because its name looks old; search all consumers and run CI first.

## 4. Source-of-truth / round-trip fix

A critical bug allowed a translated value, especially French, to be remembered as if it were the original source text. That caused mixed-language UI during later switches.

The stabilized design follows these rules:

- Arabic is the normal source-of-truth.
- Mutations generated by the translator must not be captured as new original content.
- During a non-Arabic language, arbitrary Latin/French/English text must not replace the Arabic source-of-truth.
- Dynamic presentation labels can carry `data-mizan-i18n-source` to preserve their explicit Arabic source.
- Returning to Arabic must restore the real source, not the previously selected translation.

The important acceptance sequence is:

`AR -> EN -> FR -> ID -> UR -> AR`

This sequence passed after the source-truth/cache fixes.

## 5. Protected compass and astronomical-verification scope

This is a mandatory safety boundary.

General DOM localization must not modify or rebuild operational DOM for the digital/live compass or astronomical verification.

Protected areas include, conceptually and where applicable:

- `#page-compass`
- `.qa-observatory`
- camera `video`
- operational `canvas`
- camera/sensor state
- Qibla calculation state such as QT/LAT/LON
- astronomical verification/observation state

Do not introduce camera APIs, sensor APIs, Qibla calculation variables, astronomical solver calls, or verification logic into i18n files.

Do not solve a translation gap by broadening a MutationObserver to indiscriminately translate every DOM node.

## 6. Scientific/core files

The localization project must remain presentation-only. Do not modify scientific/calculation engines as part of localization.

During pre-transfer review, key scientific files such as the astronomical solver, astro Qibla engine, astronomical verification engine, and camera pose logic were checked independently from the localization work. Future localization work must preserve this separation.

If a localization task appears to require changing a formula, solver, observation rule, camera solver, GNSS calculation state, prayer calculation engine, or Qibla engine, stop: it is outside localization scope.

## 7. Screens worked on

### Home

The Home screen has multilingual coverage and was repeatedly tested through the five-language round-trip.

Dynamic Sun/Moon presentation was adjusted so labels and scientific values are separate. Labels such as sunrise, sunset, altitude, azimuth, solar mansion, and lunar mansion can be translated without rewriting the scientific value itself.

### Prayer

Prayer-screen interface labels received multilingual coverage.

Do not alter prayer calculation logic to translate presentation text.

### Quran

Quran interface/chrome received multilingual coverage.

The Quran text itself remains Arabic intentionally. Do not translate Quran verses through the generic UI translator.

### Azkar

Azkar interface/chrome and category labels received multilingual coverage.

The Arabic dhikr content is protected. Do not use the generic UI translator to replace the actual dhikr text. Preserve source/content fields according to the existing protection rules.

### Serenity / Rahah wa Sakinah

Presentation controls received multilingual coverage.

### Falaki

A substantial part of Falaki presentation received multilingual coverage. Some text may remain untranslated intentionally where deeper intervention would threaten stability.

Do not modify astronomical calculations merely to reach 100% translation coverage.

### GNSS

GNSS is included in internal-screen language handling, but some labels may remain untranslated. This is an accepted low-priority gap if completing it would require touching live/operational GNSS behavior.

### Digital compass and astronomical verification

These are deliberately protected from broad localization intervention. Stability is more important than translating every operational label.

## 8. Internal-screen mounting issue

Several internal screens are mounted dynamically after the main language runtime has already initialized. Quran/Azkar and related presentation hosts can also use iframe documents.

`internal-screen-language-bridge.js` was introduced/expanded so the current language can be applied after an internal presentation screen is mounted, including supported iframe documents.

The bridge must remain scoped to approved presentation screens and must continue to exclude protected compass/verification areas.

## 9. Falaki performance/presentation adjustment

During localization work it was noticed that Sun/Moon event-time calculations were being requested inside a high-frequency presentation refresh path.

Presentation was adjusted so slow-changing event times (for example sunrise/sunset/noon-type event display) are not unnecessarily recalculated every second, while live altitude/azimuth presentation can continue at its required update rate.

This was a presentation/performance integration change, not a change to the astronomical formulas themselves.

Do not merge these two update rates again merely for translation convenience.

## 10. Service Worker and PWA integration

`service-worker.js` and `index.html` were reviewed as part of localization because stale caches were able to make a correct GitHub version appear broken on the phone.

The stabilized PWA work included:

- Bumping the Service Worker/cache generation for the internal i18n rollout.
- Including critical i18n/runtime/internal-screen assets in the appropriate presentation precache path.
- Ensuring old cache generations are removed during activation.
- Aligning the existing `index.html` update listener with an actual `SW_UPDATED` message from the Service Worker.
- Verifying that the page has one intended Service Worker registration path and invokes update behavior.

Do not diagnose a phone localization failure as a dictionary failure until cache generation/runtime version has been verified.

For test pages, prefer a commit-pinned URL or explicit cache-busting so the runtime version being tested is known.

## 11. Tests and safety gates

Localization work added/expanded safety gates and smoke tests covering areas such as:

- Runtime isolation from compass/camera/scientific state.
- Source-of-truth protection.
- AR -> EN -> FR -> ID -> UR -> AR round-trip.
- Dynamic source contamination scenarios.
- Internal-screen phrase coverage.
- HTML + Service Worker i18n integration.
- Falaki presentation safety.
- Pack/audit checks.

Do not rely only on a static phrase-count audit. Earlier in the project an audit reported translation coverage even though the phrases were not actually reaching the internal-screen DOM. Phone/runtime integration testing remains mandatory.

## 12. Cleanup already performed / legacy caution

Parts of the old localization architecture were removed or taken out of Production loading after proving they were unused.

Examples encountered during cleanup included old language/runtime/diagnostic paths and an obsolete global-safe i18n path.

A major lesson from this cleanup: remove one proven-unused component at a time and run the gate after each change. Do not bulk-delete legacy-looking files.

`direction.js` may still exist as a legacy/non-production-loaded file. Its existence alone is not a reason to risk another cleanup pass in the stabilized release.

## 13. Dictionary consolidation status

A consolidation experiment was started to reduce multiple phrase packs into a unified final map. Equivalence testing was introduced and the approach was technically promising.

However, final production conversion/deletion of all old packs was intentionally stopped after the application reached a stable tested state.

Handoff decision:

**Do not resume full dictionary consolidation unless there is a strong release/maintenance reason.**

It is an architectural cleanup, not a requirement for the current stable multilingual release. A future consolidation must first prove exact phrase/dynamic-pattern equivalence and then repeat phone acceptance tests.

## 14. Android widget and native notifications — NOT localized yet

This is the principal known localization work that remains.

The Android home-screen widget and native Azkar notification/notification-channel presentation still contain Arabic literals. Native localization was deliberately NOT started before this checkpoint.

Do not solve this through `english-rollout.js`, the DOM translator, or Web i18n.

The recommended architecture is Android resource localization, for example:

- `res/values/`
- `res/values-en/`
- `res/values-fr/`
- `res/values-id/`
- `res/values-ur/`

Move native user-visible strings into `strings.xml` resources and use Android resource lookup such as `getString(R.string.some_label)` / resource IDs from the appropriate native context.

Native localization must remain presentation-only and must not write or modify Qibla values, GNSS state, prayer calculations, astronomical solver output, camera/sensor state, verification state, or observation logic.

## 16. Mandatory acceptance tests for future localization changes

After any meaningful localization change, test at least:

1. Start in Arabic.
2. Switch to English.
3. Switch to French.
4. Switch to Indonesian.
5. Switch to Urdu.
6. Return to Arabic.
7. Confirm no French/English/Indonesian/Urdu text leaks into another selected language where a translation exists.
8. Confirm Arabic source restores correctly.
9. Confirm live compass still operates.
10. Confirm camera can still open from astronomical verification.
11. Confirm astronomical-verification flow can start normally.
12. Confirm computational Qibla value is not changed by language switching.
13. Open Prayer, Quran, Azkar, Serenity and Falaki after selecting a non-Arabic language; verify translation appears inside the mounted screen, not only on Home.
14. Confirm Quran verse text remains Arabic.
15. Confirm protected Azkar content remains as designed.
16. Restart/reload and confirm language persistence.
17. Test PWA/Service Worker update behavior and ensure an old cache is not masking the new runtime.
18. Test RTL for AR/UR and LTR for EN/FR/ID.

For future Native localization, add Android-specific tests for widget and notification locale behavior without changing their data values.

## 18. Files/areas that must not be changed for localization

Unless the task is explicitly re-scoped outside localization, do not change:

- mathematical formulas;
- computational Qibla engines;
- astronomical solver engines;
- astronomical verification engine logic;
- camera solver/camera pose logic;
- sensor logic;
- observation logic;
- GNSS calculation state;
- prayer calculation engine;
- QT/LAT/LON scientific state;

- operational astronomical-verification/camera DOM structure.

If a translation request appears to require one of these changes, stop and reassess the architecture instead of editing the protected core.
